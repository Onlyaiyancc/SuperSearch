# v0.1.7 正式版准备方案

## 目标与授权范围

用户选择先准备 v0.1.7，验收完成后再决定公开发布。本轮产出候选源码、安装包、便携包、校验值与对应验收记录；不公开 Release、不创建正式标签、不改写已发布 beta。

## 方案选择

1. 推荐：保持现有产品功能，修复发布验证缺口，提升内部版本，重新构建并验收。范围可控，能验证真正的 0.1.6 → 0.1.7 升级。
2. 直接将 beta.2 改为正式版：缺少跨版本升级证据，也不能解决已发现的版本硬编码，不采用。
3. 同时新增功能、全面升级依赖：扩大回归范围，延后本次准备；安全审计发现影响 Windows 的问题则单独处理。

## 改动边界

- 同步 package.json/package-lock.json、Cargo.toml/Cargo.lock、tauri.conf.json 的版本到 0.1.7；保留历史版本的测试夹具和发布记录。
- 安装验收读取已验证构建所对应源码中的版本，严格校验安装包名称、清单、PE 文件版本、基线版本及安装后版本，拒绝同版本升级冒充跨版本验证；保留原有运行器、路径、服务归属保护。
- 为正式标签提供草稿发布路径，beta 继续沿用原规则；正式版公开发布必须是后续用户明确选择的操作。草稿操作也仅在用户授权后执行。
- 首次索引先补足可诊断证据：记录引擎启动、provider 首次就绪、夹具首次命中及失败时状态；保留 120 秒截止和失败结果，不用延长超时掩盖慢索引。依据新证据再决定是否需要生产行为修复。
- 更新 README、发布指南、v0.1.7 说明和验收清单，清楚区分候选状态、旧版参考证据与本次实际结果。

## 验收与发布门槛

1. 现有前端与 Rust 回归、类型检查、构建、许可一致性、npm/Rust 依赖审计、隔离引擎烟测。
2. 对本次精确候选在可销毁的 Windows 运行器执行 0.1.6 → 0.1.7 安装升级、配置保留、服务/索引、卸载共存与全新安装；不在日常电脑安装或卸载。
3. 本次候选的原生资源诊断，记录时间、样本、内存趋势与查询失败；短时或合成诊断不证明长期无泄漏。
4. 热插拔、睡眠唤醒、真实 150%/200% DPI、缺少 WebView2/UAC 等需要合适环境与用户配合的场景，逐项列明实际状态；未执行项目不能标为通过。
5. 代码签名是发行选择：先确认可用签名配置；没有证书不伪造签名或隐去未签名状态。候选可准备，公开前向用户说明实际下载体验和验收缺口。
